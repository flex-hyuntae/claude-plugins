# Work Topic 추가

flex 시스템이 **실제로 어떻게 동작하는지** 를 노트로 남긴다. 코드를 읽어 알아낸
구조, 도구·서비스 사이의 경로, 왜 그렇게 되어 있는지가 여기 들어간다.

## 어느 층인지 먼저 가른다

| 내용 | 층 | 스킬 |
|---|---|---|
| 회사와 무관한 기술 지식 (`B-Tree 인덱스`, `React reconciliation`) | Topic | `/add-topic` |
| flex 시스템의 실제 동작 (`데스크가 지식을 참고하는 경로`) | Work Topic | 이 스킬 |
| 프로젝트 단위 요구·결정 문서 (무엇을 만들 것인가) | Spec | `/drill:plan` |

Work Topic 과 Spec 을 가르는 기준은 **시점**이다. Spec 은 만들기 전에 정하는
것(의도)이고 Work Topic 은 만들어진 것을 읽어 적는 것(현실)이다. 같은 도메인에
둘 다 있을 수 있고, 그때는 서로 링크한다.

## 0. Vault 경로 확인

vault 경로: `~/Projects/flex/wiki`
GitHub repo: `flex-hyuntae/wiki` (private)

없으면 다음 메시지를 출력하고 중단한다:

> 위키 vault 가 없습니다. 먼저 `gh repo clone flex-hyuntae/wiki ~/Projects/flex/wiki` 로 클론해주세요.

## 1. 내용 정리

- **제목**: 무엇에 대한 지식인지. 동작을 담은 구(句)로 적는다.
  좋은 예 — `데스크 에이전트가 지식을 참고하는 경로`, `Matrix 구성원 검색 흐름`.
  나쁜 예 — `search_knowledge` (심볼 이름만으로는 무엇을 아는지 안 보인다).
- **도메인**: 기존 `Work/` 서브폴더를 확인하고 고른다. 없으면 새로 만든다.
  flex 의 제품·시스템 경계를 따른다 (`AI 에이전트`, `지식관리`, `근태`, `결재`, `인프라` …).
- **태그**: 관련 키워드 (`[desk, mcp, tool-search]`)
- **repos**: 근거를 읽은 레포 이름 (`[flex-ai-backend]`)
- **verified**: 오늘 날짜. 이 노트의 사실을 언제 확인했는지다.

## 2. 기존 노트·문서 확인

세 곳을 본다. 전부 원문을 읽지 말고 인덱스로 겹침과 연결 후보만 판단한다.

1. `Work/_INDEX.md` — 같은 주제 노트가 이미 있나. 있으면 **새로 만들지 말고 갱신**한다 (아래 "이미 있는 노트를 갱신할 때").
2. `Topics/_INDEX.md` — 이 동작을 설명해 주는 개인 지식 노트가 있나. 있으면 링크한다.
3. `ls ~/Projects/flex/wiki/Spec/` — 같은 도메인 Spec 이 있나. 있으면 링크한다.

층을 넘는 연결이 이 위키의 값이다. "왜 이렇게 만들었나" 가 Spec 에 있고 "일반적으로
이런 방식을 무엇이라 부르나" 가 Topic 에 있으면, Work Topic 이 그 둘을 잇는 자리가 된다.

## 작성 규칙

### 근거 없는 문장을 쓰지 않는다 (가장 중요)

Work Topic 은 회사 코드를 보고 쓴 사본이다. **정본은 코드다.** 그래서 노트의 모든
구조적 주장은 근거를 댈 수 있어야 한다.

- `## 근거` 에 **실제로 읽은** 파일 경로를 남긴다. 줄 번호까지 적으면 나중에 되짚기 쉽다.

  ```markdown
  ## 근거

  - flex-ai-backend `jvm/common/tool-search/.../ToolSearchGroup.kt:12-40` — 상시 노출 목록
  - flex-ai-backend `jvm/api/.../McpDeskMainAgentServerAutoConfiguration.kt:71-79` — MCP 등록
  - AID-6048 · PR #4518 — 이 구조가 들어온 티켓
  ```

- **읽지 않은 것을 근거로 적지 않는다.** 추측한 경로를 적으면 다음 사람이 그걸
  믿고 코드를 안 열어 본다. 틀린 근거는 근거가 없는 것보다 나쁘다.
- 코드를 직접 못 본 사실(사람이 말해준 정책, Slack 결정 등)은 근거 칸에 출처를
  그대로 적는다 — `이명현 슬랙 2026-06-04` 처럼.

### 낡을 것을 전제로 쓴다

- **바뀔 값을 본문에 박아 두지 않는다.** 도구 개수·목록 전체를 나열하기보다
  "어디에 정의돼 있나" 를 적는다. 목록은 바뀌고 위치는 잘 안 바뀐다.
- 개수를 꼭 적어야 하면 확인 시점을 함께 적는다 — `2026-08-04 기준 15개`.
- 지금 이 순간의 임시 상태(진행 중 마이그레이션 등)는 그렇게 밝혀 적는다.

### 무엇이 남을 지식인지 가린다

전부 적으려 들면 코드의 열등한 사본이 된다. 남길 것은 **코드를 다시 읽어도 금방
안 보이는 것**이다.

- 여러 파일에 흩어져 있어서 한자리에 모아야 보이는 구조
- 이름만 보고는 알 수 없는 경계 (무엇이 무엇을 담당하지 **않는지**)
- 그렇게 된 이유 (티켓·결정 기록에만 남아 있는 배경)
- 헷갈리기 쉬운 지점 — 실제로 내가 잘못 짚었던 곳이 제일 값지다

한 파일만 열면 바로 보이는 사실은 굳이 옮기지 않는다.

### 비밀은 넣지 않는다

private 레포지만 위키는 지식을 담는 곳이고 데이터를 담는 곳이 아니다.

- 고객사 실데이터·개인정보·구성원 실명 목록 — 넣지 않는다
- 토큰·키·접속 정보 — 넣지 않는다. 있는 위치만 적는다 (`~/.config/flex/env`)
- 내부 URL·티켓 번호·PR 번호는 괜찮다

### 언어와 가독성

`/add-topic` 과 같은 규칙이다.

- 기술 용어·심볼은 영어 원문 그대로, 설명 문장은 한국어로 쓴다
- 한국어 문장이 100자를 넘으면 쪼갠다. 줄 수가 늘어나는 건 손해가 아니다
- `A = B`, `A → B`, 명사형 종결 같은 압축 문체를 쓰지 않는다
- 설명하는 말은 쉬운 말로 쓴다 (기술 용어는 예외 — 어려운 낱말이 아니라 정확한 이름이다)

### 한 개념은 한 노트가 소유한다

같은 메커니즘을 두 노트에서 각자 설명하면 반드시 어긋난다. 주인 노트를 정하고
나머지는 한 줄 + `[[링크]]` 로 위임한다. `## 연결 노트` 에는 **왜 연결됐는지**를
`—` 뒤에 붙인다. 확신이 없으면 이유를 비워 둔다.

## 3. Work 노트 생성

`~/Projects/flex/wiki/Work/<도메인>/<제목>.md` 를 만든다. 새 도메인이면 서브폴더를
먼저 만든다.

`.obsidian/graph.json` 은 **손대지 않는다.** `path:Work` 색상 그룹 하나가 이미 층
전체를 칠하고 있다 (Topics 는 카테고리별로 칠하지만 Work 는 층 단위다).

구조는 `~/Projects/flex/wiki/Templates/Work Template.md` 를 읽어서 그대로 따른다
(여기에 복사해 두면 드리프트가 생긴다). 섹션은 이렇게 채운다.

| 섹션 | 넣는 것 |
|---|---|
| `## 요약` | 이 노트가 답하는 질문 하나와 그 답 |
| `## 어떻게 동작하나` | 경로·순서·경계. 흐름이 있으면 코드 블록으로 단계를 보여준다 |
| `## 핵심 포인트` | 헷갈리기 쉬운 지점, 남들이 잘못 짚는 곳 |
| `## 근거` | 읽은 파일 경로 · 티켓 · PR (위 "근거 없는 문장을 쓰지 않는다") |
| `## Worked` | `Sources/worked.md` 에 이어지는 항목이 있으면 그 Notion URL |
| `## 연결 노트` | `[[Topic]]` · `[[다른 Work Topic]]` · Spec 문서 링크 + 연결 이유 |

`<!-- toc -->` 블록은 **비워 둔다.** 다음 단계의 스크립트가 채운다.
해당 없는 섹션은 지운다 — 빈 섹션을 남기지 않는다.

**`## 요약` 의 첫 줄은 그 자체로 완결된 한 문장으로 쓴다.** 인덱스는 첫 산문 *줄*을
요약으로 가져간다 (문장이 아니라 줄이다). 한 문장을 두 줄로 접어 쓰면 인덱스에
`…도구로만 참고한다. 대화가 시작될 때` 처럼 잘린 채 실린다. 문장이 길어지면 접지 말고
다음 문장을 새 문단으로 내린다.

Spec 은 vault 안의 일반 마크다운이라 `[[KNOWLEDGE]]` 처럼 위키링크로 걸린다.
경로가 필요하면 `[KNOWLEDGE](../../Spec/knowledge/KNOWLEDGE.md)` 로 적는다.

## 이미 있는 노트를 갱신할 때

Work Topic 은 코드가 바뀌면 낡는다. 그래서 새로 쓰는 것보다 고치러 오는 일이 많다.

1. 바뀐 문장을 고친다. 낡은 서술을 남겨 두고 새 문장을 덧붙이지 않는다 — 노트가
   자기 자신과 어긋난다.
2. frontmatter 의 `verified` 를 오늘로 갱신한다.
3. `## 근거` 의 경로가 아직 맞는지 확인한다. 파일이 옮겨졌으면 경로도 고친다.
4. **구조가 바뀐 이유를 알면 한 줄 남긴다.** "무엇이 바뀌었나" 보다
   "왜 바뀌었나" 가 다음에 값지다.

사실이 뒤집혔으면(전에 A 라고 적었는데 실제로 B) 그 사실을 보고에서 짚는다.
조용히 고치면 내가 잘못 알고 있었다는 것을 사용자가 모른다.

## 4. 생성물 갱신 (인덱스 + TOC)

```bash
cd ~/Projects/flex/wiki
python3 scripts/build-index.py
```

`Work/_INDEX.md` 와 노트별 TOC 를 다시 만들고, 100자 넘는 문장을 보고한다.
`Topics/` 와 같은 스크립트가 두 층을 함께 처리한다. 빠뜨리면 인덱스가 낡아서
다음 대화에서 이 노트가 안 보인다.

**방금 쓴 노트가 가독성 보고에 올라오면 그 자리에서 쪼갠다.** 줄번호는
`python3 scripts/build-index.py --readability` 로 본다.

인덱스와 TOC 는 생성물이므로 손으로 고치지 않는다. 요약이 어색하면 인덱스가 아니라
**`## 요약` 의 첫 줄**을 고친다.

## 5. Git 커밋 & 푸시

```bash
cd ~/Projects/flex/wiki
git status --short
git add -- "Work/<도메인>" Work/_INDEX.md
git commit -m "feat: <제목> Work Topic 추가"
git push
```

**`git add -A` 를 쓰지 마라.** 이 레포에는 다른 Claude 세션이 붙어 있을 수 있다.
남이 작업 중인 파일을 통째로 쓸어담아 커밋에 섞이는 사고가 있었다. 커밋 전에
`git status` 로 내 것이 아닌 변경을 확인하고 **경로를 명시해서** 담는다.

백링크를 넣은 기존 노트도 경로에 함께 적는다. push 가 거부되면(원격이 앞서 있음)
강제하지 말고 `git pull --rebase` 후 다시 push 한다.
