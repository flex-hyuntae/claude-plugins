# TIL 추가

사용자가 "오늘 배운거야", "TIL", "지식 기반에 추가해줘", "배운점 추가" 등으로 호출하면 다음 흐름을 따른다.

## 0. Vault 경로 확인

TIL vault 경로: `~/Projects/flex/til`
GitHub repo: `flex-hyuntae/til` (private)

해당 디렉토리가 존재하는지 확인한다. 없으면 다음 메시지를 출력하고 중단한다:

> TIL vault가 없습니다. 먼저 `gh repo clone flex-hyuntae/til ~/Projects/flex/til` 로 클론해주세요.

## 1. 내용 정리

사용자가 제공한 내용을 분석하여:
- **토픽 제목**: 배운 내용의 핵심 주제 (예: "AG-Grid 셀 상태 관리", "webpack bail 옵션과 child compiler")
- **카테고리**: 기존 `Topics/` 서브폴더 목록을 확인하고, 가장 적절한 카테고리를 선택한다. 적합한 카테고리가 없으면 새 서브폴더를 생성한다.
- **날짜**: 오늘 날짜 (YYYY-MM-DD 형식)
- **태그**: 관련 기술 키워드 (예: `[webpack, css, vanilla-extract]`)
- **본문**: 사용자가 제공한 상세 내용을 마크다운으로 정리
- **연결 노트**: 관련 있는 기존 노트를 `[[노트명]]` 링크로 연결 (다음 단계에서 인덱스로 찾는다)

## 2. 기존 노트 확인

`~/Projects/flex/til/Topics/_INDEX.md` 를 읽는다. 노트별 한 줄 요약 · 태그 · 연결 관계가 모두 들어 있어서 개별 노트를 열지 않고도 겹침·연결 후보를 판단할 수 있다.

- 내용이 기존 토픽과 겹치면 기존 노트를 업데이트할지 새로 만들지 사용자에게 확인한다.
- 관련 있는 기존 노트가 있으면 `[[노트명]]` 으로 양방향 연결한다 (새 노트에서 기존 노트 링크 + 기존 노트에도 새 노트 링크 추가).
- 인덱스 요약만으로 판단이 안 서면 해당 노트 원문만 골라 읽는다. 전부 읽지 않는다.

## 작성 규칙

### 독자 = 주니어 개발자 (가장 중요)

노트는 **해당 주제를 처음 접하는 주니어 개발자가 읽는다고 가정**하고 쉽게 쓴다. 내가 이미 이해했으니 생략해도 되겠지 하는 부분이 바로 독자가 막히는 지점이다.

- **처음 나오는 용어·이름은 그 자리에서 풀어준다.** 특히 코드 예시에 등장하는 생성된 클래스명·내부 식별자(예: `StringExtKt`, `Continuation`)는 "이게 어디서 나온 이름인지"를 반드시 한 줄 붙인다. 설명 없이 던지면 독자는 원래 알던 타입(`String` 등)과 헷갈린다.
- **결론을 던지기 전에 "왜 그런지"를 먼저 깐다.** "오버라이드 안 됨" 같은 결론은 그 앞의 원리(정적 함수로 번역된다 등)를 이해하면 저절로 따라오게 배치한다.
- **비유·대조·구체적 예시를 적극 쓴다.** 추상 설명 한 줄보다, 익숙한 것(JS·일상 비유)에 빗대거나 before/after 코드를 나란히 보여주는 게 훨씬 잘 박힌다.
- **모르는 상태에서 읽어보고, 막힐 만한 곳에 설명을 채운다.** 점프하는 논리(A라서 C다 — B가 빠짐)를 남기지 않는다.

### 언어

- 기술 용어는 영어로 작성한다 (예: reconciliation, call stack, linked list, bailout, bitmask, shallow comparison)
- 설명 문장은 한국어로 작성하되, 널리 쓰이는 기술 용어는 음역하지 않고 영어 원문 그대로 쓴다

### 가독성 — 문장 길이와 낱말 난이도

**"간결하게" 는 줄 수가 아니라 가독성이다.** 문장이 길어지거나 낱말이 어려워지면 읽기가 어려워진다. 설명을 깎아서 줄 수를 줄이는 건 위 "독자 = 주니어 개발자" 와 정면으로 충돌한다. **정리 결과를 보고할 때 줄 수 델타를 성과로 제시하지 않는다.**

- **긴 문장을 쪼갠다.** 한국어 산문이 100자를 넘으면 절이 셋 이상 붙어 있는 것이니 나눈다. 쪼개서 줄 수가 늘어나는 건 손해가 아니다.
- **압축 문체를 쓰지 않는다.** `A = B` · `A → B` · 명사형 종결("~수렴 중", "~가 현재의 약한 고리")로 눌러 담으면 짧아 보이지만, 읽는 사람이 문장을 복원해야 한다.
- **설명하는 말은 쉬운 말로 쓴다.** 기술 용어는 예외다 — 어려운 낱말이 아니라 정확한 이름이다 (위 "언어" 참고).

자주 나오는 것들 (전부는 아니다):

| 쓰지 말 것 | 대신 |
|---|---|
| 따름정리다 | 위 규칙에서 바로 따라온다 |
| 원천적으로 없다 | 애초에 없다 · 아예 없다 |
| 봉쇄한다 | 막는다 |
| 귀결 | 결과 |
| ~로 수렴한다 | ~로 정해진다 |
| 관통하는 테마 · 미학 | 전체에 흐르는 성질 |
| 해부도 | 구조 |
| 방아쇠 | 원인 |
| 상류 · 하류 | 앞단 · 뒷단 |

단, 그 낱말이 정확한 쓰임이면 그대로 둔다 — 수학적 수렴("점수가 0에 수렴"), 완화↔봉쇄 대조쌍처럼.

### 한 개념은 한 노트가 소유한다

같은 메커니즘을 두 노트에서 각자 설명하면 반드시 어긋난다. **주인 노트를 정하고 나머지는 한 줄 + `[[링크]]` 로 위임한다.**

새 노트를 쓸 때도 같다. 기존 노트에 이미 있는 개념은 다시 설명하지 말고 링크한다.

### 연결 노트에는 이유를 적는다

`- [[노트명]]` 만 적으면 왜 이어져 있는지가 사라진다. `_INDEX.md` 만 읽고도 관계가 잡히도록 **`— 왜 연결됐는지`** 를 붙인다.

연결 이유를 확신할 수 없으면 **추측해서 쓰지 말고 설명 없이 그대로 둔다.** 틀린 설명은 없는 것보다 나쁘다.

### 출처는 노트가 들고 있는다

템플릿의 `## 핵심 포인트` 와 `## 연결 노트` 사이에 세 자리가 있다. `Sources/` 의 세
파일과 하나씩 짝이 맞는다.

| 섹션 | 짝 | 넣는 것 |
|---|---|---|
| `## 아티클` | `Sources/articles.md` | 읽은 아티클 URL |
| `## Worked` | `Sources/worked.md` | 회사에서 한 일 (Notion URL) |
| `## Book` | `Sources/books.md` | 읽은 책 |

**`Sources/` 에 이 노트로 이어지는 항목이 있을 때만 채운다.** 해당하는 게 없는
섹션은 지운다 — 대화에서 바로 나온 내용이면 세 개를 다 지우게 된다. 빈 섹션을
남기지 않는다.

`Sources/` 의 `↔` 로도 이어지긴 한다. 하지만 그건 스크립트가 다시 만드는 파일에 붙은
백링크다. **"이 노트가 무엇을 읽고 쓰였나" 는 노트가 직접 들고 있어야 오래 남는다.**

여러 항목을 하나로 묶어 쓴 노트라면 묶은 것을 전부 적는다. 나중에 "이 주제로 뭘
읽었더라" 를 되짚는 자리가 된다. 항목이 많으면 `·` 로 이어 한 줄에 여러 개를 담는다.

새 노트를 만든 뒤에는 반대쪽도 채운다. `Sources/` 에서 그 항목을 찾아 `↔ (없음)` 을
`↔ [[노트명]]` 으로 바꾼다.

## 3. 토픽 노트 생성

`~/Projects/flex/til/Topics/<카테고리>/<토픽 제목>.md` 파일을 생성한다. 새 카테고리인 경우 서브폴더를 먼저 생성하고, `.obsidian/graph.json` 의 `colorGroups` 에 새 색상 그룹을 추가한다 (`query` 는 `path:Topics/<카테고리>`, `color` 는 기존과 안 겹치는 `rgb` 정수).

구조는 `~/Projects/flex/til/Templates/TIL Template.md` 를 읽어서 그대로 따른다 (여기에 복사해 두면 드리프트가 생긴다). frontmatter 만 채워야 할 값이 정해져 있다.

- `date` — 오늘 날짜 `YYYY-MM-DD`
- `tags` — 관련 기술 키워드

`<!-- toc -->` 블록은 **비워 둔다.** 다음 단계의 스크립트가 채운다.

## 4. 생성물 갱신 (인덱스 + TOC)

노트를 추가·수정한 뒤에는 **반드시** 이 스크립트를 돌린다. 빠뜨리면 `_INDEX.md` 가 낡아서 다음 대화에서 새 노트가 안 보이고, TOC 도 본문과 어긋난다.

```bash
cd ~/Projects/flex/til
python3 scripts/build-index.py
```

두 가지를 갱신하고, 하나를 보고한다.

- **`Topics/_INDEX.md`** — 노트별 요약·태그·연결 관계
- **노트별 TOC** — H1 바로 뒤 `<!-- toc -->` 블록에 H2·H3 를 중첩. 모든 노트에 넣는다 (H2·H3 가 하나도 없는 노트는 제외)
- **가독성 보고** — 100자 넘는 문장을 노트별로 세어 출력한다. 고치지는 않는다

앞의 둘은 생성물이므로 손으로 고치지 않는다. 요약이 어색하게 잡히면 인덱스가 아니라 **노트 본문의 첫 문단**을 고친다 (인덱스는 H1 다음 첫 산문 한 줄을 요약으로 쓴다). 멱등하므로 여러 번 돌려도 안전하다.

**방금 쓴 노트가 가독성 보고에 올라오면 그 자리에서 쪼갠다.** 줄번호까지 보려면:

```bash
python3 scripts/build-index.py --readability
```

기존 노트의 긴 문장까지 전부 고칠 의무는 없다. 다만 **내가 이번에 손댄 노트가 목록에 있으면 고치고 넘어간다** (위 "가독성 — 문장 길이와 낱말 난이도" 참고).

## 5. Git 커밋 & 푸시

```bash
cd ~/Projects/flex/til
git status --short
git add -- "Topics/<카테고리>" Topics/_INDEX.md .obsidian/graph.json
git commit -m "feat: <토픽 제목> 추가"
git push
```

**`git add -A` 를 쓰지 마라.** 이 레포에는 다른 Claude 세션이 붙어 있을 수 있다. 남이
작업 중인 파일을 통째로 쓸어담아 내 커밋에 섞이는 사고가 있었다. 커밋 전에
`git status` 로 내 것이 아닌 변경이 있는지 보고, **경로를 명시해서** 담는다.

백링크를 넣은 기존 노트도 경로에 함께 적는다. push 가 거부되면(원격이 앞서 있음)
강제하지 말고 `git pull --rebase` 후 다시 push 한다.
